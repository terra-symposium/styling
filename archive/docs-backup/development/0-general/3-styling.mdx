## Workflow

Styling work should move from broad structure to detail. Start with hierarchy and layout, then add
colour, typography, and polish once the interface already works.

### Design loop

The most effective workflow is cyclical rather than exhaustive. Build a simple version first, then
refine only the problems revealed by the real interface.

:::tip[Work in low fidelity]

To focus on layout and structure without distraction, sketch with a thick marker on paper or work in
greyscale first. This forces hierarchy to come from spacing, contrast, and size before colour does
the work.

:::

## Visual Hierarchy

Visual hierarchy determines what the reader notices first, second, and last. A well-designed screen
guides attention without needing labels everywhere.

### Hierarchy tools

Do not rely on font size alone to create hierarchy. Most interfaces need a restrained combination of
size, weight, and colour.

<table>
  <thead>
    <tr>
      <th align="left">🧩 Tool</th>
      <th align="left">Standard</th>
      <th align="left">Typical use</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td align="left">Size</td>
      <td align="left">
        Make important content larger, but avoid too many distinct font sizes.
      </td>
      <td align="left">Headings, totals, primary actions</td>
    </tr>
    <tr>
      <td align="left">Weight</td>
      <td align="left">
        Use heavier font weights for emphasis instead of increasing size alone.
      </td>
      <td align="left">Active states, headings, key labels</td>
    </tr>
    <tr>
      <td align="left">Colour</td>
      <td align="left">
        Reduce contrast for secondary content rather than shrinking it
        excessively.
      </td>
      <td align="left">Metadata, hints, inactive navigation</td>
    </tr>
  </tbody>
</table>

:::tip[Hierarchy trio]

Create a strong and subtle hierarchy by combining size, weight, and colour rather than overusing any
one of them.

:::

### Supporting emphasis

Hierarchy also depends on what you de-emphasise. Use background-aware text colours, softer inactive
states, and context-first phrasing to reduce clutter.

<table>
  <thead>
    <tr>
      <th align="left">🧩 Technique</th>
      <th align="left">Standard</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td align="left">Coloured backgrounds</td>
      <td align="left">
        On coloured surfaces, use a related hue with adjusted saturation and
        lightness instead of generic grey text.
      </td>
    </tr>
    <tr>
      <td align="left">Relative emphasis</td>
      <td align="left">
        Make important elements stand out by softening the competing ones around
        them.
      </td>
    </tr>
    <tr>
      <td align="left">Avoid labels</td>
      <td align="left">
        Prefer context-rich phrasing over <code>label: value</code> formatting
        when the layout already provides meaning.
      </td>
    </tr>
  </tbody>
</table>

### Spacing system

A systematic approach to spacing makes layouts easier to reason about. Use Tailwind's built-in scale
rather than arbitrary pixel values.

<table>
  <thead>
    <tr>
      <th align="left">🧭 Principle</th>
      <th align="left">Tailwind practice</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td align="left">Use a system</td>
      <td align="left">
        Use built-in spacing utilities such as <code>p-4</code>,{" "}
        <code>m-6</code>, and <code>space-y-8</code>.
      </td>
    </tr>
    <tr>
      <td align="left">Constrain width</td>
      <td align="left">
        Use <code>max-w-*</code> or <code>@apply container</code> to control
        line length and readability.
      </td>
    </tr>
    <tr>
      <td align="left">Flexible grids</td>
      <td align="left">
        Use <code>flex</code> and <code>grid</code>, with fixed widths such as{" "}
        <code>w-64</code> where sidebars need stability.
      </td>
    </tr>
    <tr>
      <td align="left">Group with space</td>
      <td align="left">
        Use larger margins between sections than within them, such as{" "}
        <code>space-y-4</code> inside a card and <code>mb-12</code> between
        cards.
      </td>
    </tr>
  </tbody>
</table>

:::caution[Grouping rule]

To visually group related items, make the space between groups at least twice as large as the space
within a group. This creates clearer, more scannable sections.

:::

### Responsive structure

Layouts must degrade cleanly on smaller screens. Preserve hierarchy and grouping when columns stack
or sidebars collapse.

<table>
  <thead>
    <tr>
      <th align="left">📱 Concern</th>
      <th align="left">Standard</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td align="left">Reading width</td>
      <td align="left">
        Constrain long-form content with <code>max-w-*</code> or{" "}
        <code>max-w-prose</code>.
      </td>
    </tr>
    <tr>
      <td align="left">Sidebars</td>
      <td align="left">
        Use stable widths on large screens, then collapse or stack them on
        mobile.
      </td>
    </tr>
    <tr>
      <td align="left">Grid density</td>
      <td align="left">
        Prefer fewer columns on smaller screens rather than shrinking content
        until it becomes cramped.
      </td>
    </tr>
    <tr>
      <td align="left">Grouping rhythm</td>
      <td align="left">
        Preserve the same between-group and within-group spacing ratio on
        mobile.
      </td>
    </tr>
  </tbody>
</table>

### Responsive priority

When space is tight, preserve hierarchy first, then preserve decoration. Content should stack before
it becomes visually cramped.

### Font selection

Typeface quality matters. A few simple heuristics help you choose fonts that stay legible under real
UI conditions.

<table>
  <thead>
    <tr>
      <th align="left">🔎 Heuristic</th>
      <th align="left">Description</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td align="left">Play it safe</td>
      <td align="left">
        A neutral sans-serif or the native system stack is a reliable default.
      </td>
    </tr>
    <tr>
      <td align="left">Weights</td>
      <td align="left">
        Typefaces with five or more weights tend to be more flexible and
        polished.
      </td>
    </tr>
    <tr>
      <td align="left">Legibility</td>
      <td align="left">For body text, choose fonts with a large x-height.</td>
    </tr>
  </tbody>
</table>

### Readability rules

Readable typography depends on more than type size. Line length, alignment, and line height should
all reinforce the content's density and role.

<table>
  <thead>
    <tr>
      <th align="left">🧩 Concern</th>
      <th align="left">Standard</th>
      <th align="left">Example</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td align="left">Line length</td>
      <td align="left">
        Keep lines between 45 and 75 characters for long-form readability.
      </td>
      <td align="left">
        <code>max-w-prose</code>, <code>prose</code>
      </td>
    </tr>
    <tr>
      <td align="left">Alignment</td>
      <td align="left">
        Align mixed-size text on the baseline rather than the visual centre.
      </td>
      <td align="left">Metric + unit on one line</td>
    </tr>
    <tr>
      <td align="left">Line height</td>
      <td align="left">
        Use taller leading for small text and long lines, shorter leading for
        large headings.
      </td>
      <td align="left">
        <code>leading-relaxed</code>, <code>leading-tight</code>
      </td>
    </tr>
  </tbody>
</table>

## Components

Component styling should stay consistent with the existing system. Prefer composing reliable
building blocks over hand-rolling one-off UI primitives.

### Shadcn usage

Components are sourced from [Shadcn](https://ui.shadcn.com/docs/components), with minimal alteration
to fit Terra Symposium's visual language.

      <td align="left">
        Preserve layout stability so buttons and cards do not jump during async
        work.
      </td>
    </tr>
    <tr>
      <td align="left">Status cues</td>
      <td align="left">
        Do not rely on colour alone to communicate success, warning, or error.
      </td>
    </tr>
  </tbody>
</table>

### Motion

Motion should support comprehension, not decorate empty space. Keep it purposeful, restrained, and
compatible with accessibility preferences.

<table>
  <thead>
    <tr>
      <th align="left">🎞️ Rule</th>
      <th align="left">Standard</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td align="left">Purpose</td>
      <td align="left">
        Use animation to explain entry, hierarchy, or state change.
      </td>
    </tr>
    <tr>
      <td align="left">Restraint</td>
      <td align="left">
        Prefer a few meaningful motions over constant micro-animations.
      </td>
    </tr>
    <tr>
      <td align="left">Accessibility</td>
      <td align="left">
        Respect reduced-motion preferences where movement is non-essential.
      </td>
    </tr>
  </tbody>
</table>

### State priority

If motion and clarity conflict, clarity wins. A state change must remain obvious even when reduced
motion is enabled.

## Iconography

Icons should come from the approved source for the environment they appear in. Keep the visual
vocabulary consistent across the web app and the CMS.

### Icon sources

Choose the icon library based on runtime context, not personal preference. The import path should
make that choice obvious.

### Source priority

Choose the icon set by environment first, then by metaphor. Do not mix libraries arbitrarily within
the same context.

### Astro icons

Icons for the web application should come from
[Carbon Icons](https://carbondesignsystem.com/guidelines/icons/library/). Keep class names
consistent with the surrounding typography and spacing.

```astro
---
import IconName from '~icons/carbon/hyphenated-name-of-icon';
---

<IconName className='inline align-[-.16em] text-2xl text-black' />
```

### Sanity icons

Icons in the CMS should use Carbon Icons where possible, and
[Sanity Icons](https://icons.sanity.build/all) only when the Carbon set does not provide the needed
metaphor.

```ts
import { DocumentIcon } from '@sanity/icons';

preview: {
	prepare({ title }) {
		return {
			title,
			media: DocumentIcon,
		};
	},
},
```

### Reserved icons

Some icons are reserved for fixed meanings. They must remain exclusive to those contexts so the
visual language stays stable for users.

:::caution[Reserved icons]

These icons must always be used in their reserved contexts and never repurposed for other meanings.
